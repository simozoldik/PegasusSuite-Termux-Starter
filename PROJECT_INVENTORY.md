## 2. Android wrapper and native integration method

- **Host activity:** `MainActivity extends com.getcapacitor.BridgeActivity`. It registers three custom plugins *before* `super.onCreate()`:
  `CellTowerPlugin`, `PhoneScannerPlugin`, `WiFiCrackerPlugin` (`MainActivity.java` lines 14–21).
- **Integration method:** Capacitor custom plugins (Java), invoked from JS via `window.Capacitor.Plugins.*`.
  The frontend calls them through a `callPlugin(...)` helper (`frontend/app.js`).
- **Generated wiring:** `android/capacitor.settings.gradle` and `android/app/capacitor.build.gradle` are auto-generated by `cap sync` (header says "DO NOT EDIT").
- **Plugins actually bundled** (from `@capacitor` deps): `app`, `keyboard`, `splash-screen`, `status-bar` (+ core/android). `capacitor.plugins.json` in the APK assets lists registered plugins.
- **Web asset pipeline:** `scripts/build-web.js` copies `frontend/` → `www/` (Capacitor `webDir` is `www`, per `capacitor.config.json`), and the Android assets copy lives at `android/app/src/main/assets/public/`. **These `www/` and `assets/public/` trees are build outputs and were intentionally NOT collected** (they are generated copies of `frontend/`).
- **Preferred WebView scheme:** `https://localhost` (`capacitor.config.json` → `server.androidScheme: "https"`), so `frontend/config.js` uses an **absolute** `apiBaseUrl` (`http://192.168.1.137:8710`) because a relative `/api` would resolve against the WebView itself.

## 4. Existing scanning / discovery mechanisms and their entry points

### Frontend (PHONES tab and siblings)
- Tab registry in `frontend/app.js` (~line 317): `phones: { label: 'Nearby phones', scan: scanPhones }`.
- `scanPhones(runId)` (~line 487) calls the backend and renders the radar + device list.
- Native plugin calls from the frontend:
  - `callPlugin('PhoneScanner', 'deviceInfo', ...)` (used in more than one place, ~lines 344, 362)
  - `callPlugin('WiFiCracker', 'scan', ...)` (~line 460)
  - `CellTower` is referenced in the module doc comment (~line 4).
- `HACK NOW` flow (~line 567) posts to `/phone/audit` and polls `/phone/audit/:jobId`.

### Native plugins (Java)
- **PhoneScannerPlugin** — `deviceInfo()` returns `{ wifiEnabled, localAddresses[], arp[] }`. Reads `/proc/net/arp` and local interfaces. Read-only; performs no active scan itself.
- **WiFiCrackerPlugin** — `scan()` returns `{ accessPoints[{ssid,bssid,rssi,frequency,security}], count }` from `WifiManager.getScanResults()`. Does **not** capture handshakes or crack keys.
- **CellTowerPlugin** — `getCells()` returns `{ towers[{type,cellId,lac,mcc,mnc,registered,rssi}], count, networkOperator }` from `TelephonyManager.getAllCellInfo()` (LTE/GSM/WCDMA). Requires runtime location permission.
- **No BLE / Bluetooth plugin is present** in the collected native sources or the Capacitor dependency list (**observation**: there is currently no BLE scanning capability in the app).

### Backend
- `POST /api/lan/scan` → bounded TCP-connect host discovery (`lanAudit.scanHosts`).
- `GET  /api/lan/subnets` → private subnets of the backend host.
- `POST /api/camera/audit` → camera-focused TCP/HTTP/RTSP fingerprint.
- `POST /api/location/triangulate` → cell-tower multilateration (`cellTriangulation.triangulate`).
- `POST /api/camera/scan-plan`, `GET /api/camera/rtsp-urls` → RTSP planning (`cameraHacker`).
- `POST /api/wifi/parse-handshake`, `POST /api/wifi/crack-plan` → `.22000` parsing / hashcat plan (no execution) (`wifiCracker`).
- `POST /api/phone/scan-plan` → plan stub (reuses `cameraHacker.buildScanPlan`; probes list = `['arp','icmp','tcp:80','tcp:443','tcp:62078','mdns']`).
- `POST /api/phone/discover` → **live nearby-phone discovery** (`phoneAudit.discoverPhones`).
- `POST /api/phone/audit`, `GET /api/phone/audit/:jobId`, `POST /api/phone/audit/:jobId/cancel` → 9-step per-phone audit job.
- `GET /api/security/all` → aggregate capability report.

**Discovery pipeline (from `phoneAudit.js` header — describes `POST /api/phone/discover`):**
1. pick the backend's private IPv4 subnet (or caller CIDR);
2. read Windows ARP table (`arp -a`) + default gateway (`route print -4`) + Wi-Fi SSID/band (`netsh wlan show interfaces`, FR/EN parsers);
3. bounded-concurrency ICMP ping-sweep of the /24 and merge fresh ARP entries;
4. quick TCP probe of phone-signature ports (ADB / iOS lockdown / AirPlay / Cast);
5. classify every host via the IEEE OUI database (`backend/src/data/oui-phones.json`) into phone/router vendors;
6. best-effort mDNS + NBNS + SSDP/UPnP identity;
7. ICMP RTT per host treated as real Wi-Fi proximity → nearest phones listed first.

## 5. Exact endpoint and data format used by the PHONES screen

- **Endpoint:** `POST {apiBaseUrl}/api/phone/discover` with JSON body `{}` and a 120 s client timeout (`frontend/app.js` line 491; `apiUrl()` prepends `/api`, line 20–23).
- **Backend route:** `POST /api/phone/discover` → `phoneAudit.discoverPhones({ cidr, timeoutMs, concurrency })` → `res.json(result)` (`backend/src/routes/security.js` lines 184–196).

**Response fields consumed by the frontend** (`frontend/app.js` lines 493–532, direct evidence of the shape read by the UI):
- `subnet` (string, e.g. `192.168.1.0/24`)
- `network` (object; `type`, `gateway`)
- `devices[]` — each device uses: `ip`, `type` (`'phone'` for identified phones), `mac`, `macKind` (`'randomized'`), `openPorts[]`, `rttMs`, `proximity`, `reachable`, `label`, `ssdp.{server,st}`, `network`
- `phones[]` — identified phones subset (used for the count).

**Radar/proximity mapping (observed intent):** blip radius derives from measured `rttMs`; colors are green = identified phone, amber = possible phone (randomized MAC), cyan = other device.

> The full server-side return object in `phoneAudit.js` was not reproduced line-by-line here; the fields above are those the frontend reads. Extra server fields may exist — treated as **not exhaustively enumerated**.

## 6. Current Android permissions and platform restrictions

From `android/app/src/main/AndroidManifest.xml`:

- `INTERNET`, `ACCESS_NETWORK_STATE`
- `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION` (required by Android to read cell info / Wi-Fi scan results)
- `ACCESS_WIFI_STATE`, `CHANGE_WIFI_STATE`
- `NEARBY_WIFI_DEVICES` with `android:usesPermissionFlags="neverForLocation"`
- `<uses-feature android:hardware.telephony/wifi required="false">`

Application flags: `usesCleartextTraffic="true"` + `android:networkSecurityConfig="@xml/network_security_config"`.

**Platform restrictions relevant to a discovery engine (evidence-based):**
- Location permission is mandatory for `getScanResults()`, `getAllCellInfo()` and `NEARBY_WIFI_DEVICES`; without it the plugins reject.
- `targetSdk 35` means `NEARBY_WIFI_DEVICES` is the Wi-Fi scanning permission on Android 13+.
- **No BLE/Bluetooth permissions are declared** (`BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT` absent) → any future BLE scanning needs new manifest permissions.
- No `POST_NOTIFICATIONS`, no background service, no `FOREGROUND_SERVICE` declared → discovery currently runs only while the app/WebView is active.

**Network security config (release):** cleartext HTTP is permitted globally (`base-config cleartextTrafficPermitted="true"`) plus explicit domains `192.168.1.137`, `192.168.1.85`, `10.27.1.18`, `10.0.2.2`, `localhost`, `127.0.0.1`. The file itself flags this as **TEST ONLY** and states it MUST be reverted to `false` before production. A separate `src/debug/res/xml/network_security_config.xml` exists for debug builds.
